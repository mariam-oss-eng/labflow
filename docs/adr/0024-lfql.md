# ADR-0024: LFQL — a tiny boolean query language for tasks

* **Status**: accepted (v0.16)
* **Context**: Smart lists (v0.13) shipped a JSON-shaped filter — fine
  for an API but awful for humans typing into a search box or for
  describing a scheduled report's audience in one line. A growing
  pile of features (smart lists, scheduled reports, ad-hoc CLI
  queries) needed *the same* filter semantics in *the same* notation.
* **Decision**: Ship a small boolean DSL — **LFQL** — with hand-rolled
  tokenizer, parser, and AST evaluator, exposed via
  `GET /api/lfql/{explain,run}`.

## Grammar (informal)

```
expr   := orexpr
orexpr := andexpr ( "OR" andexpr )*
andexpr:= unary  ( "AND" unary )*
unary  := "NOT" unary | "(" expr ")" | atom
atom   := key op value
op     := ":" | ":>" | ":<" | ":>=" | ":<=" | ":!="
```

Examples:

```
status:open AND owner:alice
priority:>=high AND title:"login bug"
NOT status:done AND created:>2026-01-01
```

## Why a custom DSL (and not GraphQL filters / raw SQL)

* **Auditability**. Operators paste an LFQL string into a postmortem
  and everyone can read it. SQL would leak schema; GraphQL filter
  shapes don't survive the URL bar.
* **Safety**. The parser rejects unknown fields and operators *before*
  any DB call, so no field-name typo silently filters to "everything".
* **Reusable**. The same AST powers REST listing, scheduled reports,
  and (in the future) HTMX search. Compare to v0.13 smart lists which
  re-implemented filtering inline.

## Why in-memory eval

The current scale (≤ tens of thousands of tasks per team) fits a
single SQL pre-filter on `team_id` followed by Python evaluation in
microseconds per row. The trade-off is one extra Python loop in
exchange for **zero** extra SQL surface — significant since a SQL
translation would have to handle owner joins, NULL semantics for
priority comparisons, and string-vs-substring operators per dialect.
A future `to_sql()` projection is possible without changing the
parser API.

## What we sacrifice

* No regex / fuzzy matching. The `key:value` operator is substring
  for strings (case-insensitive) which covers the common case.
* No date arithmetic (`created:>now-7d`). Clients render absolute
  timestamps; LFQL parses ISO-8601 strings only.
