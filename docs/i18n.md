# Internationalisation (v0.9)

LabFlow ships a tiny dict-based message catalogue with RFC 7231
`Accept-Language` negotiation. The default catalogue covers **English,
Spanish, and French**; adding a locale is a single PR to
`labflow/i18n.py`.

## Endpoints

| Method | Path | Returns |
|---|---|---|
| `GET` | `/api/i18n/locales`              | `{"locales": ["en", "es", "fr"]}` |
| `GET` | `/api/i18n/messages?locale=fr`   | Full catalogue for the chosen locale |
| `GET` | `/api/i18n/messages` (no `locale`) | Catalogue for the negotiated locale |

The negotiation respects `q=` weights and falls back to the primary
subtag (`fr-CA` → `fr`). When no requested tag is supported, returns
the first configured locale (English by default).

## Configuration

```bash
export LABFLOW_LOCALES=en,es,fr,de
```

Locales not in the catalogue are filtered out at startup, so adding
`de` alone has no effect until a `_CATALOGUES["de"]` entry exists in
`labflow/i18n.py`.

## Adding a locale

1. Open `labflow/i18n.py`.
2. Add a new entry to `_CATALOGUES` keyed by the BCP 47 locale tag.
   Provide every key from the `en` catalogue.
3. Add the locale to `LABFLOW_LOCALES` (or accept the default which
   includes `en`, `es`, `fr`).
4. Open a PR. No build step required.

## Programmatic use

```python
from labflow.i18n import t, negotiate

loc = negotiate(request.headers.get("accept-language"))
title = t("app.title", locale=loc)
```

Missing keys fall back to the English string, so a new key shipping in
a single PR doesn't break non-English UIs — they just see the English
text until the translation lands.
